# 食谱本（CookbookTool）

Android 端的**纯本地**食谱工具：记食谱、记每天吃了什么。不联网，不申请网络权限，数据只在本机。

- 包名 `org.miu.cookbook`，minSdk 26（Android 8.0），targetSdk 35
- Kotlin + Jetpack Compose (Material 3) + Room
- 侧边栏两个主界面：**食谱**（默认）和**饮食历史**

## 一条核心设计原则：Markdown 不是数据库格式

需求里说食谱正文"以 markdown 形式存储展示"，但实现上反过来：

| | 存什么 | 为什么 |
|---|---|---|
| 数据库 | **结构化数据**：原料是独立表的行（名字/数量/量词/顺序），做法和备注是带 `level`（缩进层级）的有序列表项 | 拖动排序、行首空格调整缩进、句号转三级标题，这些操作在结构化模型上都是确定性的；直接改 Markdown 字符串则每次按键都要重新解析，且 CommonMark 的列表缩进规则会频繁和"两个空格一行"的直觉冲突 |
| Markdown | **只是序列化结果**，用于展示和导出 | 生成器有 bug 只会显示难看，不会损坏数据；而且未来做"食材清单/保质期"需要跨食谱查食材，文本里查不了 |

## 构建

本机 `$HOME` 只读、且没有 JDK/SDK，所以工具链装在工作区 `.toolchain/`（已在 .gitignore）。

```bash
bash scripts/setup_toolchain.sh   # 首次：下载 JDK 21 + Android SDK 35 + Gradle 8.9，约 2GB
bash scripts/build.sh             # 默认 assembleDebug
bash scripts/build.sh test        # JVM 单测
```

产出的 APK：

- 调试包 `app/build/outputs/apk/debug/app-debug.apk`（包名带 `.debug`，可以和正式包并存）
- 正式包 `app/build/outputs/apk/release/app-release.apk`（`bash scripts/build.sh assembleRelease`）

正式包的签名口令放在工作区的 `keystore.properties`（和 `keystore/` 一起 gitignore）。
文件不在时会退回 debug 签名，这样别人 clone 下来也能直接 `assembleRelease` 出包装机。
**故意没开 R8**：kotlinx-serialization 和 Room 的 keep 规则没有真机验证过，
压缩出问题只有运行时才发现，等真机跑通一轮再开。

用 Android Studio 打开也可以，但需要本机有 JDK 17+ 与 Android SDK 35，
并让 Gradle 能写 `$HOME`（或设 `GRADLE_USER_HOME`）。

## 装到手机上

```bash
adb install -r app/build/outputs/apk/release/app-release.apk     # 正式包，包名 org.miu.cookbook
adb install -r app/build/outputs/apk/debug/app-debug.apk         # 调试包，包名带 .debug，可与正式包并存
```

也可以把 APK 拷进手机点开安装（需要在系统里允许"安装未知来源应用"）。
不需要任何权限：没有 INTERNET，也没有存储/相机权限（拍照走系统相机、选图走 Photo Picker）。
数据全在应用私有目录里，卸载即丢——所以换机前记得先用顶栏「⋮」导出备份。

## 数据模型要点

- `recipe` — 菜名、创建/更新时间（H1 菜名不存进正文，只在序列化时生成），外加同步要用的
  三件套：`uuid`（跨设备身份）、`deleted_at`（删除墓碑）、`dirty`/`server_rev`（待上传标记与
  最后见到的服务端版本）
- `content_block` — 做法/备注的行，`section`（DIRECTIONS/NOTE）+ `kind`（有序列表项/三级标题）+ `level`（缩进层级）
- `ingredient` — 原料名 + 食材数（文本，允许"适量"）+ 量词（可为空串）
- `category` / `recipe_category` — 分类是 tag，多对多；分类也带 `uuid`（两台设备各自建的「家常菜」
  要认得出是同名但不同身份的两条）
- `recipe_image` — 相对 `filesDir` 的路径 + 缩略图 + 顺序 + 是否列表封面
- `meal_log` — `epoch_day` + 餐段（早/午/晚）+ 食谱；查"每道菜最后一次被吃"用于未来的加权随机
- `sync_state` — 只有一行，记本机标识与"已经拉到哪个版本号"；**配对令牌不在这里**
  （导入备份会 `clearAllTables()`，令牌放这儿会被一次「导出再导入」弄丢）

餐段判定（`MealTime`）：02:00–10:29 早餐，10:30–15:29 午餐，其余晚餐；
其中 00:00–01:59 算作**前一天**的晚餐。

删除食谱是**软删**：行留着、打上 `deleted_at` 墓碑并标脏（"这道菜被删了"这件事要能同步给家人），
原料与正文跟着墓碑一起留着，等墓碑到期清理时才由 `ON DELETE CASCADE` 带走。
图片行与饮食记录是**本机数据**，删除时立刻清掉（删除前会提示影响条数）——
而家人删掉这道菜时（同步推来的墓碑）只打墓碑，本机的饮食记录和图片不动：
"我上周三吃过这道菜"是自己吃过的历史，不该因为别人删了菜谱就消失。

搜索（`FuzzySearch`）全在内存里做，不走 SQL：菜名先比前缀、再比子串，然后是**逐字子序列**
（输"番炒"能命中"番茄炒蛋"），最后是**拼音首字母子序列**（输"fqcd"也能命中）；
分类、原料也参与匹配但排在菜名后面。拼音表由 `scripts/gen_pinyin_table.py` 从 Unihan 生成，
多音字（如"茄" jiā/qié）两个声母都认，所以 fqcd 和 fjcd 都搜得到。

## 编辑行为的一处约定：全程即时落盘

菜名、分类、原料、做法、备注都是**边编边存**，没有「取消 / 完成」按钮：

- 菜名停下来 400ms 写一次（`RecipeDetailScreen` 里的 `titleDirty` + 防抖 `Job`），退出编辑态时补写；
- 原料和做法 / 备注两个子编辑器共用 `ui/recipes/edit/DebouncedSaver.kt` 的
  `rememberDebouncedSaver`：停手 400ms 写一次，**离开页面时把最后没写的那一下补上**；
- 补写挂在 `AppContainer.appScope`（活到进程结束）上——页面自己的 `rememberCoroutineScope`
  会随页面销毁被取消，最后一下改动就丢了；
- 分类勾一下就存。

写回是整份替换（`replaceIngredients` / `replaceContent`：先删后插，走一个事务）。
所以：

- 拖动排序、行首空格缩进、句号转三级标题，全是对界面草稿里的小数据做确定性变换，不碰数据库；
- 空行在存库前会被丢掉（结构化模型里它没有意义，Markdown 解析时也一样）。

Markdown 的读写都在 `RecipeMarkdown` 里（`serialize` / `parse` 互为逆运算，有 round-trip 单测）。
详情页右上角的「Markdown」按钮可以把当前这道菜导出成 Markdown 并复制走。

## 图片：一律复制进私有目录

`ImageStore` 把选中的图（拍照得到的临时文件、相册给的 content Uri 都走同一条流）解码后
**压到长边 2048 再写进 `filesDir/images/`**，另存一份长边 320 的缩略图到 `filesDir/thumbs/`，
数据库里只记相对路径。不保留原图：SAF 授权会过期、相册里的原图也可能被删，留个路径迟早变死链。
解码前先用 `inJustDecodeBounds` 读尺寸算采样率，不然一张 12MP 的照片按原尺寸就是 48MB 内存；
EXIF 方向会按 Matrix 转正，横着拍的照片进详情页不会歪。

拍照/选图都不需要权限：拍照交给系统相机 App（结果写进自己 `FileProvider` 暴露的
`cacheDir/camera/` 临时文件，`file_paths.xml` 只暴露这一个目录），选图用 Photo Picker
（Android 13+ 原生，以下自动退回文件选择器）。

图片的删、换序、设封面都是**立即写库**的，没有草稿——和正文编辑不同，图片本身已经在磁盘上，
攒草稿反而要处理"拍完照又取消"这种边界。封面永远有且只有一张：删掉当前封面时自动落到第一张。

## 饮食历史：一天一行，倒着排的列表

`meal_log` 里 `slot` 存的是枚举名（TEXT），所以**不能交给 SQL 排序**——字母序会得到早/晚/午。
分组和排序都在 Kotlin 里做（`MealHistoryUiModels.toHistoryDays`：先按 `epochDay` 分组，
每天内按 `MealSlot.ordinal` 再按记录时间排）。列表用 `LazyColumn(reverseLayout = true)`：
index 0 是最新的一天、落在屏幕底部，正好是"默认停在最下方、向上拖动回溯"。

历史页的查询是一条手工 JOIN（食谱标题 + 封面子查询），不是 Room 的 `@Relation`——后者
每个关联都要多查一次，一天三顿饭就是几十次查询。

记录一顿有两种入口：食谱列表页非编辑态的加号（进"记录模式"：50% 黑蒙版 + 搜索栏自动聚焦，
挑一道菜再弹确认窗；退出靠顶栏的返回箭头、点蒙版、安卓返回键），以及详情页右下角的加号
（直接记当前这道菜）。确认窗里的日期/餐段
默认按当前时间推（`MealTime.resolve`），日期既能左右翻一天、也能点开日历直接挑；
**翻过日期之后再改餐段不会把日期拽回去**。
在记录模式里再按一次加号 = 先新建食谱，再拿它弹确认窗（也可以"只保存，不记录"）。
**新建食谱时如果搜索栏里有字，会把它当默认菜名填进去**。

同一天同一餐可以记多道菜。改某一餐的去处用的是
`MealLogDao.moveOrSwapSlots(fromDay, fromSlot, toDay, toSlot)`：**日期和餐段都能改**
（人经常把日期记错），目标那一餐**已经有记录就整餐交换**（跨天也一样，界面弹一句提示），
空着就直接搬过去。整餐（可能好几道菜）一起换，谁都不会丢。

## 备份与恢复：一个 zip，导入即整库替换

顶栏右上角的「⋮」是导出 / 导入备份，走 SAF（`CreateDocument` / `OpenDocument`），
不需要任何存储权限。备份文件就是：

```
cookbook.json          数据（可读的 JSON，图片按文件名引用）
images/ab12.jpg        原图（长边 2048 那份）
thumbs/ab12.jpg        缩略图
```

用 zip 而不是把图片 base64 塞进 JSON：图片占备份体积九成以上，base64 还要再涨三分之一，
而且解压时得把整个 JSON 读进内存。`cookbook.json` 本身是可读的，出问题能直接打开看。

导入是**整库替换**（不做合并），所以先弹窗说清会覆盖掉什么。安全性上做了三件事：

- 图片先解到 `restore-tmp/`，等数据库那边成功写完才换目录，中途失败不会留「库里有图、磁盘上没有」；
- 数据库那边包在一个事务里（`clearAllTables` + 按原 id 写回），失败整个回滚；
- 被引用的东西缺了就丢掉那条引用（图片文件丢了、分类 id 不存在），而不是让整个导入失败——
  备份文件可能是手改过的。zip 条目名会做目录穿越检查。

备份文件是**外部输入**，所以只在导入侧做的一半校验后来补齐了（一次只读审查的结论）：

- JSON 里的图片路径也过一遍校验（不能以 `/`、`\` 开头，不能含 `..`，规范化之后必须仍在
  自己的私有目录里）——否则 `File(baseDir, "/data/.../x.jpg")` 会忽略 `baseDir`，
  导入一个手改的备份就能删/读私有目录外的文件；越界的图片直接丢掉那条记录。
- 每道菜最多留 `MAX_RECIPE_IMAGES`（=6）张图，超出的丢掉；这个上限同时收进了
  `CookbookRepository.addImage`，不再只靠界面藏起加号。
- `epoch_day` 必须落在 `0..MAX_EPOCH_DAY` 内再入库——`Long.MIN_VALUE` 正好是整餐交换用的
  中转哨兵值，混进来会把两条记录一起搬错；越界的饮食记录直接丢掉。
- 缩略图文件缺失时把 `thumb_path` 存成空串，让读取时 `thumbPath.ifBlank { path }` 的回退生效。

主键 id 原样保留，所以食谱-分类-图片-饮食记录之间的引用关系不会错位。

## 家庭共享的同步服务端

一家人各自的手机各存一份库、各拍各的照，**没有中心服务器就没法共享**。所以有了这一块：
一个跑在家里 NAS 上的小服务端，加上 App 里的同步引擎与设置页（M8 已完成）。

三个模块的分工：

- `:sync-model` —— 两端共用的**线上格式**（`SyncRecipePayload`、`SyncRecord`、`PushRequest`…）。
  共用一份是为了不出现「两端字段各写各的」这种最费时间的错位。它故意不带本机自增 id 和
  图片路径：换台设备那些东西就没有意义了，图片改用内容哈希 `sha256` 引用。
- `:sync-server` —— 服务端。**零第三方框架**：HTTP 用 JDK 自带的 `com.sun.net.httpserver`，
  数据库用 `sqlite-jdbc`，JSON 复用 kotlinx-serialization（这台开发机拉不到 Ktor/Netty 之类
  的新依赖，家用 NAS 上其实也不需要）。
- `app`（`data/sync/`）—— 同步引擎：`SyncCredentials`（令牌存 SharedPreferences）、
  `SyncApi`（`HttpURLConnection`，不引 OkHttp）、`SyncStore`（库 ↔ 线上载荷的双向转换）、
  `SyncEngine`（拉 → 推 → 再拉一轮）。设置页在侧边栏「设置」里。

一键自检（起一个临时实例，真用 curl 走完整流程，跑完自动清理）：

```bash
bash scripts/sync-server-check.sh
```

手动起服务：

```bash
bash scripts/build.sh :sync-server:fatJar
.toolchain/jdk/bin/java -jar sync-server/build/libs/sync-server-all.jar --port 18088 --data ./data
# 启动日志里的 PAIR_CODE= 就是配对码；也写在 <data>/pair-code.txt
```

用 Docker 起（NAS 上推荐）：

```bash
bash scripts/sync-server-image.sh          # 开发机上打镜像 cookbook-sync:1
cd deploy && docker compose up -d --build  # 数据落在 deploy/data/
```

**一步步装到 NAS 上的完整步骤（含只跑镜像的 compose、systemd 路线、备份与恢复、排错表）
见 [deploy/README.md](deploy/README.md)。** 备份不用停服务：

```bash
docker compose exec cookbook-sync \
  java -jar /app/cookbook-sync.jar --backup /data/backup-$(date +%F).db
```

接口（都在这几个路径上，`Authorization: Bearer <令牌>`）：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/v1/health` | 体检：水位、活着的食谱数，不需要令牌 |
| POST | `/api/v1/pair` | 拿配对码换设备令牌（一次性码 10 分钟有效，用过即换） |
| GET | `/api/v1/sync?since=<水位>&limit=<条数>` | 增量拉取 |
| POST | `/api/v1/sync` | 推送增量（`upserts` + `deletes`） |
| PUT/GET | `/api/v1/blobs/<sha256>` | 传/取一张图，按内容寻址 |
| POST | `/api/v1/blobs/check` | 一次问「这些图你缺哪些」 |

几条容易写错、所以记下来的同步语义：

- **每条记录带自己的 `rev`，水位按记录推进**。拉取的 `nextSince` 是本次最后一条的 `rev`，
  **不是**服务端全局水位——用全局水位的话，分页途中别人一写，中间那几条就被永久跳过了。
  推送响应的 `serverRev` 也不要拿来推进 `lastRev`（推送期间别人可能推高它）。
- **冲突按 `updatedAt` 比，败方存成新 uuid 的副本**，菜名由服务端加「（冲突副本）」后缀。
  删除不产生副本。`baseRev`（客户端上次见到的水位）用来判断「这条记录你见过没有」：
  `server_rev > baseRev` 才算冲突，否则直接覆盖。
- **删除是墓碑不是物理删**：30 天内谁都能拉到「这条没了」，之后由服务端清理线程物理删。
  客户端收到墓碑只打标记，不动本机的饮食记录与图片。
- **图片先传后推**：客户端先 `blobs/check` 问缺哪几张、PUT 上去，再推记录。服务端因此只在
  「上传超过 24 小时且没人引用」时才删孤儿图，避开「图传完了、记录还没推上来」的空窗期。
- **限流分开两档**：同步接口按设备限流（默认 240/分钟），图片单独一档（1200/分钟，首次同步
  可能要传几百张）。配对接口按来源 IP 限流——**只有来源地址在可信反代名单里才认
  `X-Forwarded-For`**，否则伪造一个头就绕过去了。

### 手机上怎么用

装好 App 后，侧边栏 →「设置」→ 家庭共享：

1. **服务器地址**填在外面也能连上的那个：公网域名（套了反代就是 `https://cookbook.example.com`；
   直接暴露端口就是 `http://家里公网地址:18088`）。别填 `127.0.0.1`，那是手机自己；
2. **局域网地址**（可选）填 `http://192.168.1.10:18088`。填了之后在家优先走它——
   不少路由器不支持从内网访问自己的公网地址，硬走公网会连不上，而且绕一圈也慢；
3. 配对码填服务端 `data/pair-code.txt` 里的那六位（十分钟失效，但**服务端会自动换新的**并把文件改写掉，
   所以文件里永远是当前有效的那个，过期了也不用重启容器）；
4. 点「配对」。

**地址是怎么选的**：每次同步按「局域网 → 上次连上的 → 公网」的顺序试，前面的连不上就换下一个，
最后一个才会等满超时。所以在家一条内网请求就完事，在外面也不会卡在一条不通的地址上两分钟；
设置页里「服务端」那一行显示的是这次真正连上的地址。局域网地址留空就一直是公网直连。

**什么时候同步**：配对完、打开应用、从编辑页退出来（按返回或点「完成」）、从详情页回到列表、
以及手动点「立即同步」。编辑是即时落盘的，退出编辑后一秒半内没有新的改动就会自动推一轮——
在几个编辑器之间来回按返回只会合并成一次。

同步范围与边界（都是刻意选的）：

- **同步的是菜谱**：菜名、分类、原料、做法/备注、图片。**饮食记录不同步**——哪天吃了什么是各家的私事。
- 两边都改过同一道菜时两边各留一份：晚改的保留原名，早改的变成「××（冲突副本）」。
  首页顶上有一条提示，删掉不要的那份它就自己消失了。
- 服务端的令牌放普通 SharedPreferences（manifest 已经是 `allowBackup="false"`，adb 与云备份都拿不到）。
  这台开发机拉不到 `androidx.security`，所以没有用 EncryptedSharedPreferences。
- **没有 WorkManager**（`androidx.work` 同样拉不到），所以没有真正的后台定时同步：
  触发点是「打开应用 / 编辑完 / 回到列表 / 手动」，应用完全退到后台后就不再跑。
  菜谱本来也不需要秒级同步，定时同步留给以后要加的时候再说。
- 图片按内容寻址存成 `images/<sha256>.jpg`：同一张图被两道菜用到只存一份，换台设备路径也依然有效。
  v2 时代的老图第一次同步前补算哈希。删图时**不删磁盘文件**（可能还有别的菜引用同一份内容），
  孤儿文件暂时不回收。
- 局域网明文 HTTP 要在 `res/xml/network_security_config.xml` 里放行——`targetSdk 35` 默认禁明文。
  公网暴露时请套反代上 HTTPS（服务端认 `X-Forwarded-For` 只信可信来源，见下）。
- 导入备份会把同步游标一起清掉（整库替换）。已配对时导入完会自动重拉、再推一遍本地，
  两边都改过的那几道菜会各留一份副本——这是可以接受的，覆盖导入本来就该谨慎用。

## 几条界面约定

- **顶栏常驻**：进详情页、进任何一个子编辑器，顶栏都不消失也不换行（那样点进点出会
  "标题栏闪一下再播切换动画"）。各页只提供"标题 + 动作"两样东西给顶栏：详情页的标题在
  「食谱详情」和「编辑食谱」之间切，只读时的动作是「Markdown + 铅笔」，编辑态是空的；
  原料 / 做法备注的标题是区块名，动作是空的（它们即时落盘，不需要按钮）；图片编辑页标题
  是「图片」，它自己的操作（N/6、设为封面、删除）留在页内那一条黑栏上。食谱名只在正文里出现。
- **详情页 ⇄ 编辑态是淡入淡出**（`RecipeDetailScreen` 里的 `Crossfade`，顶栏标题也跟着淡入淡出）：
  这两个状态在同一个 composable 里，不走 NavHost 的页面切换动画，不自己加一层就会"瞬间跳过去"，
  跟别的页面切换的观感不一致。
- **全程即时落盘，没有「取消 / 完成」**：菜名停下来 400ms 写一次，退出编辑态时补写；
  分类点一下就存；原料和正文两个子编辑器也一样，停手 400ms 写一次，退出页面时把最后
  没写的那一下补上。补写用的是 `AppContainer.appScope`（活到进程结束的作用域）——
  页面自己的 `rememberCoroutineScope` 会随页面销毁被取消，最后一下改动就丢了。
  所以编辑页只有一个返回箭头，没有别的按钮。
- **提示走应用自己的 Snackbar，不用系统 Toast**：Toast 的样式由系统决定，日夜模式切不动。
  统一从 `ui/components/Messenger.kt` 的 `LocalMessenger` 走。Snackbar 的默认配色是
  `inverseSurface`（日间黑底、夜间白底，跟整个界面反着来），所以这里显式改成
  `surfaceContainerHigh` + `onSurface`，圆角 16dp。
- **量词是个下拉框**（`ExposedDropdownMenuBox` + 只读输入框），不是文字按钮 ——
  文字按钮没人看得出能点。可选量词只有 g/kg/ml/L/个/根/片/块/颗/把/勺/杯 和空，
  只、条、粒、张、段、朵、束、碗这几个重复或适用面窄的已经去掉。
- **从列表长按「编辑食谱」进去的详情页，返回直接回列表**（这个页面本来就是奔着编辑来的），
  从只读详情点铅笔进的编辑态才"先退编辑态、再退页面"。判据是 `RecipeDetailState.enteredAsEditor`。
- **一级入口都在顶栏「⋮」里**：导出备份 / 导入备份 / 多选。列表页和历史页里原来那两个
  编辑图标已经去掉，多选统一从「⋮」进。
- **食谱页左侧那条分类栏只属于食谱页**（不是能从屏幕边缘拉出来的抽屉，不能滑开滑关，宽度固定
  104dp，从顶栏下面一直到底）。从上到下三段：全部 / 自己挑的分类（太长就 5 个字 + 省略号）/
  底部「编辑分类」。列表里放哪些分类、什么顺序、当前选中哪个都存 SharedPreferences 并按 **uuid**
  记（导入备份换了库也对得上），不进数据库也不同步——侧栏长什么样是这台设备的看法。
  **选中分类的口径分两档**：没在搜索时**只看这个分类的菜**；一旦输入了搜索词就**不过滤**，
  带这个分类的排到最前、其余照旧按匹配度跟在后面。分类单选，再点一次保持选中，
  只有点「全部」能清掉；某个分类下一道菜都没有时，空状态说的是「这个分类还没有食谱」。
- **记录模式的退出在顶栏上，面板里只有「搜索框 + 加号」**：最早最左边是个 ×（看着像清空输入，
  其实是退出记录），后来改成面板里的返回箭头——但这一行本来就挤，窄屏或侧栏展开时
  「吃了什么？」会被压到两行。现在记录模式把顶栏换成「← 记录饮食」、右边两个按钮全收起，
  48dp 还给输入框；输入框里的放大镜也去掉了（只是装饰）。退出三条路：顶栏返回、点蒙版、
  安卓返回键，**不**给输入框加清除按钮。
- **顶栏那个转圈箭头是同步**（只在食谱页出现，历史的饮食记录本来就不同步）：跑的时候变成转圈，
  完事弹一句「同步完成：收到 N 条，发出 M 条」（有冲突副本时单独说），没配对就直接提示去设置里配。
  它和设置页的「立即同步」是同一条路（`SyncEngine.syncNow()`），只是多了这条提示。
- **安卓返回键先退模式再退页面**：记录模式 → 多选 → 搜索词，逐层收；详情页编辑态先退出
  编辑态。不会一按就回到桌面。
- **外观在设置页里**（跟随系统 / 日间 / 夜间），存 SharedPreferences（为这一个开关引
  DataStore 不划算）。主题状态放在 `CookbookTheme` 外面，否则改了不生效。侧边栏最下方只留
  一个「设置」入口，不再把三项外观直接铺在抽屉里。
- **设置页自己不带顶栏**：标题与返回箭头由 `CookbookRoot` 的 `TopAppBar` 统一提供，
  里面再套一个 `Scaffold` 就会出现两条标题、两个返回按钮。
- **叫法统一**：应用名「食谱本」，功能名一律用「食谱」（不再出现「菜谱」）。
- **正文的几级标题展示时不画井号**，字号拉开层级：一级 28sp、二级 22sp、三级 18sp、正文 16sp
  （`ui/recipes/MarkdownStyles.kt` 里的 `Mdh1Style/Mdh2Style/Mdh3Style/MdBodyStyle`，
  展示和编辑用同一套，别各写各的）。编辑态同理，`BasicTextField` 的 TextStyle 必须显式带
  `onSurface` 颜色，否则夜间模式下会退回黑色（这是真机上发现的）。
- **改某天的一餐是"交换"不是"合并"**：目标那一餐已经有记录就整餐换位（跨天也一样），
  界面弹一句"两餐已经交换"；空着就直接搬过去。三条 UPDATE 借 `Long.MIN_VALUE` 当
  中转日子完成，见 `MealLogDao.moveOrSwapSlots`。
- **输入法弹出时编辑区自己让位**：两个编辑器的滚动容器都带 `imePadding()`，正在编的行
  不会被键盘压住。

## 已知边界

- **真机验证过一轮**（Android 8.0+ 装得上、侧边栏能点、模糊搜索与 SAF 跳转正常）。
  这台开发机没有 `/dev/kvm`，起不了模拟器，所以剩下的触摸细节、系统相机、Photo Picker
  还是只能装到手机上试。141 个 JVM 单测覆盖了领域逻辑、Room 读写、备份 zip、同步引擎和主要界面
  （Robolectric 里跑 Compose），其中 8 个是数据库迁移测试（v1→v2→v3：自己造一个老版本的库
  再让 Room 升上来，数据没丢、且迁移出的表结构 Room 认），12 个是同步引擎的端到端测试
  （**进程内起一个真服务端**，用两套独立的库假装两台手机）；另有 24 个服务端测试
  （`bash scripts/build.sh :sync-server:test`，真起进程内 HTTP 服务）。**侧边栏条目的点击在 Robolectric 里不正常**（触摸会被抽屉
  蒙版吃掉，怀疑是测试环境的问题），这个在真机上确认是好的。
- **lint 目前 0 error、41 warning**，剩三类都是预期内的：`GradleDependency` / `AndroidGradlePluginVersion`
  （这台机器离线，依赖版本是照缓存里有的钉死的，不随手升）、`ObsoleteSdkInt` 指着
  `mipmap-anydpi-v26`（试过改成 `mipmap-anydpi`，AAPT 直接报找不到 `@mipmap/ic_launcher`，
  自适应图标必须带 `-v26`，这条当误报看）、`DataExtractionRules`（`allowBackup="false"` 已经
  关了备份，`data_extraction_rules.xml` 只是给 Android 12+ 留个明确的说法）。
  跑法：`bash scripts/build.sh lintDebug`。
- **Robolectric 里不要测"弹窗里带输入框"的流程**：`AlertDialog` 里只要放 `OutlinedTextField`，
  Compose 就永远 idle 不下来（`AppNotIdleException`，有时直接 OOM）。带输入框的弹窗只能人工验。
- **R8 没开**（见上），正式包和调试包体积差不多。
- 正文里的 Markdown 特殊字符（`#`、`-`、`|`）不做转义，导出成 Markdown 后原样呈现。
- 备份导入是整库替换，不合并。
- **NAS 部署这条路没有在这台机器上实跑过**（这台开发机没有 docker，也没有 NAS）。
  `deploy/` 里的 Dockerfile、两个 compose、systemd unit 与 Caddy 样例都是按着服务端的
  命令行/环境变量写的，服务端本身有 23 个测试 + `scripts/sync-server-check.sh`
  的 8 步 curl 自检覆盖（自检脚本会真的跑一次 `--backup`）；但镜像能不能在 UGOS 上起来、
  卷的权限对不对，要装的时候才知道。
- **同步的定时是「打开应用时 + 手动」**：没有引入 WorkManager（开发机拉不到这个依赖），
  所以 App 不在前台时不会自己同步。
- 需求里提过的两个未来扩展**都没做**：按上次吃的时间加权随机抽菜、食材清单与保质期提醒。
  数据层已经留好了口子（`MealLogDao.lastCookedDays()` 返回每道菜最后一次被吃的天数）。
